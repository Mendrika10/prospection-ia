## Constats

### 1. Important — `status = 'error'` bloque sa campagne aussi longtemps que `running`

La règle du §2 de l'ADR 0006 dit « tous statuts confondus », et c'est bien ce que fait la vue
(`max(runs.started_at)`, sans filtrer le statut). Mesuré :

| Sonde | Situation | Résultat |
|---|---|---|
| A | dernier run en `error` il y a **2 min**, intervalle 1440 → due ? | **due = 0** (bloquée) |
| A2 | même campagne, run en `error` il y a **90 min**, intervalle 60 → due ? | **due = 1** |

Conséquence : **une collecte qui échoue n'est pas relancée avant un intervalle complet** — 24 h
par défaut. Or l'ADR 0006 ne nomme, dans ses *Conséquences*, que le revers du run resté bloqué en
`running` (« on ajoutera une règle de péremption ») ; le cas `error` n'y est pas discuté, et le
test ne l'exerce **pas** (contrôle 6 pose un run `running`). Le comportement existe donc, mais il
n'est ni testé ni arbitré.

*Correction attendue* : un arbitrage écrit — soit distinguer `running` (bloquant) de `error`
(relançable), soit assumer le délai — et un contrôle de test sur `error`, quel que soit
l'arbitrage. Aujourd'hui, la seule façon de le savoir est de le mesurer.

### 2. Moyen — `runs.items_processed` reste nullable, donc le « sens unique » de D-002 n'est pas tenu

Mesuré : `information_schema.columns.is_nullable = **YES**` pour `runs.items_processed`, et un run
écrit avec `items_processed = NULL` est **accepté** par la base.

D-002 dit « `items_processed` = nombre de lignes **écrites** » — un sens **unique**. Un `NULL`
rouvre l'ambiguïté que le ticket a fermée : un run sans valeur ne dit pas « zéro ligne écrite ». La
migration crée la colonne en `default 0` mais ne la rend pas `not null`, et le test n'insère que la
valeur qu'il vient de choisir (12) : il ne peut pas voir ce trou.

*Correction attendue* : une migration **nouvelle** (la 3 est appliquée, donc immuable) rendant la
colonne `not null default 0` avec reprise des lignes existantes — ou, si `NULL` doit signifier
« inconnu », l'écrire et le distinguer explicitement de zéro. Un ticket, pas un correctif glissé
dans une PR en review.

### 3. Mineur — `prochain_run` vaut `NULL` pour une campagne due jamais exécutée

Mesuré : campagne jamais exécutée → présente dans `campaigns_due` (donc **due**), et
`prochain_run = NULL`.

Un écran qui afficherait « prochaine exécution » n'afficherait donc rien, précisément pour les
campagnes qui attendent leur premier passage — celles sur lesquelles on veut cliquer en premier.
`dernier_run` vaut `NULL` à raison (il n'y en a pas) ; c'est `prochain_run` qui est trompeur, car la
prochaine exécution est **maintenant**.

*Correction attendue* : soit renommer (`echeance_calculee`), soit `coalesce(dernier_run + interval,
now())`, soit commenter la vue pour dire que `NULL` = « premier passage ». La documentation actuelle
de la vue ne le dit pas.

## Points que je n'ai pas pu vérifier (et que je n'approuve donc pas)

- **Le comportement sur le vrai projet Supabase** : les mesures ci-dessus viennent d'un Postgres 16
  jetable. Le projet réel est en **17.11** et n'a encore reçu aucune migration (vérifié par API :
  0 table). Le verrou `S0-04` tient toujours, donc **je n'approuve pas `S1-08`/`S1-09` sur leur
  environnement cible**.
- **La relecture en contexte neuf** : non faite (voir la limite d'indépendance).
- **Le comportement à l'échelle réelle** : 100 005 runs est une charge synthétique. Le plan de la
  vue est bon à ce volume, ce qui ne prouve rien à 10⁶ — mais rien n'indique de dégradation : la
  lecture reste un `max()` par campagne due, servi par l'index partiel.
- **La cadence réelle de n8n** : `S1-09` fournit la brique `campaigns_due`, mais c'est `S1-01` (WF1)
  qui l'appellera. Rien ici ne prouve que le workflow lira la vue plutôt que `campaigns where active`.
